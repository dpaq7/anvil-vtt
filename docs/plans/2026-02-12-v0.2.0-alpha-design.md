# Anvil v2 — v0.2.0 Alpha Design

**Date:** 2026-02-12
**Status:** Approved
**Goal:** Feature-complete alpha with full player agency, all scene types interactive, basic audio playback, and demo-quality robustness.

---

## Overview

v0.2.0 transforms Anvil from a Director-only tool into a full multiplayer VTT. Five workstreams deliver: (1) complete player battle experience with Draw Steel initiative, (2) interactive non-battle scenes, (3) audio playback, (4) ability resolution engine backed by game data, and (5) polish for MCDM community demo readiness.

---

## Workstream 1: Player Battle Experience

### PlayerView Layout

```
┌──────────────────────────────────────────────────┐
│  Top Bar (hero name, session info, connection)    │
├────┬──────────────────────────────────────────┬───┤
│    │                                          │   │
│ L  │       Battle Canvas                      │ R │
│    │   (fog-filtered, hero-centered)          │   │
│    │                                          │   │
│    ├──────────────────────────────────────────┤   │
│    │  Ability Bar (hero's abilities)          │   │
├────┴──────────────────────────────────────────┴───┤
│  Status Bar (HP, conditions, turn indicator)      │
└───────────────────────────────────────────────────┘
```

- **Left rail:** Hero sheet summary (stamina, recoveries, conditions, heroic resource, equipment)
- **Right rail:** Combat log, party vitals
- **Bottom ability bar:** Hero's abilities as clickable cards, grayed when used/unavailable
- **Canvas:** Same `BattleCanvas` component with `role="player"` prop enabling fog filtering and restricting interaction to owned tokens

### Token Ownership & Movement

- Server validates `move_token` by checking if the sending user's `hero_id` matches the entity's source hero
- Player can only drag tokens they own
- `InteractionManager` receives `ownedEntityIds` prop — only those tokens are draggable
- Movement is optimistic on client, confirmed by server broadcast

### Fog of War (Player Perspective)

- `FogLayer` in player mode renders all Director-placed fog rectangles as solid black
- Tokens inside fog are hidden from the player's render
- No editing tools available for players
- This is "Director-painted fog" — not automatic line-of-sight (future enhancement)

### Targeting & Ability Use

1. Player clicks an ability card → `InteractionManager` enters `target` tool mode
2. Valid target tokens get a highlight ring (pulsing border)
3. Player clicks a target → client sends `use_ability { abilityId, sourceEntityId, targetEntityIds }`
4. Server resolves: rolls dice, calculates tier, applies damage/effects, broadcasts `ability_resolved`
5. All clients see the result (damage number, stamina bar change, combat log entry)

### Turn Actions

- Player sees action economy checkboxes (main action, maneuver, move, triggered)
- Checkboxes auto-mark when actions are used
- Server validates turn order — player can only act on their turn

## Workstream 1b: Draw Steel Initiative System

### Rules

1. **Roll to determine first side:** Server rolls 1d10. ≥6 = heroes first, ≤5 = villains first
2. **Sides alternate:** When all entities on one side have acted, the other side goes
3. **Hero turns are claimed, not assigned:** On the heroes' side turn, ANY player can volunteer. Players strategize who should act first
4. **Villain turns are Director's choice:** Director picks which monster/villain acts
5. **Round completes** when ALL entities on both sides have acted
6. **Surprise:** If one side has surprise, they automatically go first

### CombatState (Redesigned)

```typescript
interface CombatState {
  round: number;
  activeSide: 'heroes' | 'villains';
  firstSide: 'heroes' | 'villains';
  initiativeRoll: number;
  heroEntities: string[];
  villainEntities: string[];
  actedThisRound: string[];
  activeEntityId: string | null;
  malice: number;
  turnActions: Record<string, TurnActionState>;
}
```

### CombatActions (Redesigned)

```typescript
type CombatAction =
  | { type: 'START_COMBAT'; heroEntityIds: string[]; villainEntityIds: string[] }
  | { type: 'END_COMBAT' }
  | { type: 'CLAIM_TURN'; entityId: string }
  | { type: 'SELECT_TURN'; entityId: string }
  | { type: 'END_TURN' }
  | { type: 'ADJUST_MALICE'; delta: number }
  | { type: 'APPLY_DAMAGE'; entityId: string; amount: number }
  | { type: 'APPLY_HEALING'; entityId: string; amount: number }
  | { type: 'APPLY_CONDITION'; entityId: string; condition: string }
  | { type: 'REMOVE_CONDITION'; entityId: string; conditionId: string };
```

### Turn Flow

1. **Start Combat** → Director clicks "Start Combat" → server rolls 1d10 → determines first side → broadcasts
2. **Claim Turn (heroes)** → Player clicks "Take My Turn" → server validates hero hasn't acted → sets `activeEntityId`
3. **Select Turn (villains)** → Director clicks villain → server sets `activeEntityId`
4. **End Turn** → Active entity clicks "End Turn" → moves to `actedThisRound` → if all on current side acted, `activeSide` flips
5. **End Round** → When both sides fully acted → `round++`, `actedThisRound` clears, `activeSide` resets to `firstSide`, heroic resources generated

### CombatTracker UI

- Two columns: Heroes | Villains
- Acted entities grayed/checked off
- Active entity highlighted with glow
- "Take My Turn" button for players when heroes' side and their hero hasn't acted
- "Select Next Villain" prompt for Director on villain side
- Round counter with malice display

## Workstream 1c: Ability Resolution Engine

### Server-Side AbilityResolver

Located in `SessionRoom`, validates and resolves ability usage:

1. **Validate ownership** — sender owns the source entity
2. **Validate turn** — it's the source entity's turn (`activeEntityId` matches)
3. **Validate action economy** — action type is available via `BattleLogic.canUseAction()`
4. **Validate resource cost** — hero has enough heroic resource (deduct on use)
5. **Validate distance/range** — `AbilityLogic.parseDistance()` + entity positions
6. **Roll dice** — `RollLogic.calculatePowerRoll()` with characteristic + edge/bane
7. **Calculate damage** — `AbilityLogic.calculateTierDamage()` with kit bonuses
8. **Apply effects** — update target stamina, mark action as used
9. **Generate heroic resource** — trigger-based gains (damage dealt, etc.)
10. **Broadcast** — `ability_resolved` to all clients

### Universal Combat Actions

Add to `@anvil/data/rules/universal-actions.ts`:

- **Catch Breath** (maneuver) — spend 1 recovery, regain recovery value HP
- **Free Strike** (free action) — basic weapon attack on opportunity
- **Grab** (maneuver) — opposed Might test, applies grabbed condition
- **Knockback** (maneuver) — opposed Might test, forced movement
- **Hide** (maneuver) — stealth check vs enemies
- **Stand Up** (maneuver) — end prone condition
- **Resist** (maneuver) — save vs active condition

### Heroic Resource Generation

`BattleLogic.CLASS_HEROIC_RESOURCE_CONFIG` already defines per-class triggers. Wire into turn lifecycle:

- Turn start → `calculateTurnStartResource()` → add to hero's resource pool
- Cap at min/max bounds via `capHeroicResource()`
- Talent's Clarity can go negative (min: -10)

### Summoner & Minion System

Types exist in `@anvil/types` (Squad, Minion, Champion, Portfolio). Implementation:

- **MinionLayer** on battle canvas — render squads as grouped tokens
- **Squad management UI** — summon, sacrifice, move squads
- **Essence tracking** — automatic gain at turn start (+2), on minion death (+1)
- **Squad stamina pool** — shared HP with auto-death when threshold reached
- Reference Mettle codebase (`/projects/Mettle`) for validation patterns
- Reference `docs/Draw Steel v101/summoner v1.0.md` for mechanics

### What Stays Manual (Alpha)

- **Condition effect resolution** — Director reads effect text, applies manually
- **Triggered action detection** — No automatic prompts
- **Area effect targeting** — Player selects targets manually
- **Duration tracking** — "Until end of turn" tracked mentally

## Workstream 2: Non-Battle Scene Interactivity

### Negotiation Scene (Live)

**New WebSocket Messages:**
```
Client → Server:
  negotiation_argument { skillId, approachText }
  negotiation_adjust_patience { delta }           // Director only

Server → Client:
  negotiation_updated { interest, patience, argumentLog[] }
```

**Flow:**
1. Director sets up NPC motivations/pitfalls in scene data (already in builder)
2. Player selects a skill → sends `negotiation_argument`
3. Server rolls power roll + skill modifier → `NegotiationLogic.getInterestChange()`
4. Server broadcasts updated state + argument log entry
5. Director can manually adjust patience for roleplay moments

**Player UI:** Skill selector + "Make Argument" button. NPC portrait, interest bar, patience countdown, argument history.

### Montage Scene (Live)

**New WebSocket Messages:**
```
Client → Server:
  montage_roll { skillId, characteristicId }

Server → Client:
  montage_updated { successes, failures, testLog[], outcome? }
```

**Flow:**
1. Player selects a skill → sends `montage_roll`
2. Server rolls power roll + characteristic → `RollLogic.getTestOutcome()`
3. Server updates counts, checks if limits reached
4. Broadcasts updated state. If outcome determined, broadcasts that too

**Player UI:** Skills list, "Attempt Test" button, progress bars (successes/failures vs limits), test log.

### Respite Scene (Live)

**New WebSocket Messages:**
```
Client → Server:
  respite_choose_activity { activityId }
  respite_complete_activity { activityId }

Server → Client:
  respite_updated { activities: ActivityState[], completedBy: Record<string, string[]> }
```

**Flow:**
1. Director configures available activities (already in builder)
2. Players browse activities → select one → sends `respite_choose_activity`
3. Server validates (exclusivity check for limited activities)
4. Director marks activities complete when appropriate
5. All clients see who's doing what and completion status

**Player UI:** Activity cards with "Choose This" buttons. Shows who's doing what. Progress indicators.

### Story Scene (Live)

**New WebSocket Messages:**
```
Server → Client:
  story_updated { readAloudText, directorNotes }
```

Director types/reveals read-aloud text, all players see it in real-time. No player actions needed.

## Workstream 3: Audio Playback

### Architecture

- Director picks a track from audio library → sends `audio_play` via WebSocket
- Server broadcasts R2 URL + playback command to all clients
- Each client plays audio via HTML5 `<audio>` element
- Volume is local client preference (not synced)

### WebSocket Messages

```
Client → Server:
  audio_play { audioAssetId, loop: boolean }    // Director only
  audio_pause {}                                 // Director only
  audio_stop {}                                  // Director only

Server → Client:
  audio_command { action: 'play' | 'pause' | 'stop', audioUrl?, assetName?, loop? }
```

### Behavior

- Default `loop: true` for ambient tracks
- Director UI: play button with loop toggle (🔁 icon)
- Audio persists across scene changes unless explicitly stopped
- One track at a time (no layering for alpha)
- No crossfading, no playlist/queue
- Player UI: small AudioPlayer widget in status bar (track name, play/pause, local volume)

## Workstream 4: Polish & Robustness

### Toast Notifications

- shadcn/ui Sonner integration
- Server validation errors → red toasts
- Success confirmations → brief green toasts
- Connection changes → amber toasts

### Loading States

- Scene switching: loading skeleton
- Ability resolution: spinner on ability card
- Asset operations: skeleton loaders
- "Go Live": connecting state indicator

### Error Recovery

- WebSocket reconnection with exponential backoff (already implemented)
- After reconnect: full state refresh via `request_state`
- Server rejects → revert optimistic update + show toast
- DO hibernation → `ensureHydrated()` recovers from D1

### Player Disconnection

- Token stays on board (no auto-removal)
- Director sees "Disconnected" badge on participant
- Reconnecting player gets full state and resumes
- Director can act on behalf of disconnected player

### Input Validation

- Server validates all messages (ownership, turn order, resources)
- Malformed messages return `error` with descriptive code
- Client-side pre-validation (disable buttons when unavailable)

### Demo-Critical Edge Cases

- Director closes browser → DO stays alive, players see toast, Director can rejoin
- Two players claim turn simultaneously → server accepts first, rejects second
- Player moves wrong token → server rejects, client shows toast
- Large session (50+ entities) → eager loading handles it
